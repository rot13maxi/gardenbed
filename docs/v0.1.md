# gardenbed v0.1 — design and verification plan

Status: proposed. Target: ~13 weeks (the roadmap's weeks 1–12 plus a
hardening week). Every milestone below carries **verification criteria** —
the tests that tell us we built the right thing, not just that the thing
runs.

---

## 0. North star

v0.1 proves the full loop end to end. The acceptance test is an automated
demo script (`demo/run-v0.1.sh`) that must pass from a clean container:

1. `arboretum import --from <pinned real git repo>` — history ≥ 1 GB packed,
   ≥ 50k commits.
2. `bed clone <server>` — a sparse bed, materializing nothing, in < 5 s.
3. `bed plot add <subtree>` — every materialized file byte-identical to
   `git show <sha>:<path>`.
4. `bed sow -m "..."` — new changeset queryable via API in < 1 s.
5. Export back to git: `git push --dry-run` to a local mirror succeeds;
   `git fsck` on the result is clean.
6. An MCP client answers blame/log/diff questions with **no working copy
   anywhere on the machine**.

A human should never have to eyeball this — the script asserts each step.

## 1. Scope

**In:** single-repo `arboretum` (self-host single binary: sqlite seedbed +
filesystem loam), gRPC protocol, `bed` commands `clone / plot / goto /
status / file / log / diff / sow / graft / harvest`, rootstock import and
export, first-parent blame, ancestry skip list, MCP with four tools
(`log`, `diff`, `blame`, `file`).

**Out (and when it returns):**

| Deferred | Lands |
|---|---|
| nursery regional cache tier | v0.2 |
| scarecrow daemon (fs watch, shared node cache) | v0.2 |
| server-side merge with content resolution | v0.2 |
| multi-repo server (API carries a `repo` field from day one) | v0.2 |
| GC / prune | v0.2 |
| offline sow queue | v0.2 |
| FUSE / virtualized checkout | v0.3 |
| IAM / authn-z | v0.3 |
| Windows, LFS, submodule recursion | v0.3 (gitlink entries round-trip verbatim; no recursion) |

## 2. Architecture (v0.1)

```
bed ──gRPC (unix socket or TCP)── arboretum (single binary)
                                   ├─ seedbed: sqlite  (changesets, refs,
                                   │                    git-SHA mapping, derived)
                                   └─ loam: fs CAS     (blobs, trees; zstd)
```

- `bed` embeds the client: treestate in `.bed/`, object cache in
  `.bed/objects/`. **No daemon in v0.1** — scarecrow arrives in v0.2 with
  filesystem watching and cross-job cache sharing. Deliberate simplification
  vs Scion; the RPC surface is identical either way.
- All object access is **want-list**: the client resolves `RootTree(cs)`,
  then requests missing trees/blobs recursively with bounded parallelism.
  Every request names a content-addressed object, so any tier can answer it
  and any interrupted session resumes exactly.

## 3. v0.1 decisions

- **D1 — Canonical encoding: hand-rolled byte format** (spec in §4).
  Rejected: protobuf (not canonical across implementations), postcard
  (deterministic but Rust-coupled, no standalone spec), canonical CBOR
  (viable, more machinery than we need).
- **D2 — Blob identity = SHA-256 of raw content**; stored form is
  `{u64 raw_len, zstd frame}`. Compression is a storage detail, never
  identity. Whole-blob objects in v0.1; chunking (FastCDC) deferred to v0.2.
- **D3 — Trees are derived and materialized eagerly on write** (only touched
  directories), cached in loam. Export and checkout want trees immediately;
  lazy derivation for cold history is a v0.2 option.
- **D4 — RPC = gRPC (tonic)**, `.proto` lives in `protocol`; the proto plus
  §4 together form the published protocol. Convenience RPCs that break
  cacheability (e.g. "stream me a subtree") are deliberately absent.
- **D5 — No merge command in v0.1.** `harvest` = fast-forward CAS;
  `graft` = server-side linear replay, conflicts are hard errors. Merges
  enter the repo via rootstock import (we read merges fine; we don't make
  them yet).
- **D6 — Import via gitoxide** (packfile read); **export via `git
  fast-import`** subprocess. Native pack writing replaces export in v0.2;
  fast-import is battle-tested and unblocks the roundtrip-SHA criterion now.
- **D7 — Blame is defined as first-parent lineage blame with rename
  following**, semantically anchored to `git blame --first-parent`. Stated
  in CLI help; merges are blamed through first parent only (Scion's footnote
  convention).
- **D8 — Import rename detection via `git diff-tree -M --name-status`** per
  commit (subprocess) in v0.1; replaced by gitoxide rename support when it
  matures. The throughput cost is accepted and measured (M3).

## 4. Canonical encoding (spec v1)

**Rules.** Integers are LEB128 varints; signed integers are zigzag-varints.
`str` = varint length + UTF-8 bytes; `bytes` = varint length + raw bytes;
`opt<T>` = `0x00` (absent) | `0x01` + T; sequences = varint count + elements.
Encoders emit fields in spec order regardless of construction order and emit
minimal-length varints; decoders reject trailing bytes, non-minimal
varints, and unknown data. The version byte participates in the hash.

**Changeset** — format byte `0x01`, version byte `0x01`:

| Field | Encoding |
|---|---|
| parents | varint n, then n × 32 raw bytes |
| changes | varint n, then n × `{ op: u8, path: str, blob: opt<32B>, src_path: opt<str>, mode: u8 }` |
| op | 0 add · 1 modify · 2 delete · 3 rename |
| mode | 0 regular · 1 exec · 2 symlink · 3 gitlink |
| message | str |
| author | `{ name: str, email: str, time_secs: u64, tz_min: i32 }` |
| committer | same shape as author |
| signature | opt<bytes> |

Timestamps keep git-native **seconds + tz offset** (not normalized ms):
preserving both exactly is what makes the roundtrip-SHA criterion (M5)
possible.

**Tree** — format byte `0x02`, version `0x01`; entries sorted by raw name
bytes; file entry `{ name, kind=0, mode, blob_id }`, dir entry
`{ name, kind=1, tree_id }`. A tree's `Id` = SHA-256(canonical tree bytes),
which is why identical trees reached via different histories share one
object.

**Identity.** `Changeset::id` and `Tree::id` = SHA-256 over canonical bytes.
`Blob::id` = SHA-256 over raw content (D2).

## 5. Protocol sketch

```
service Gardenbed {                        // repo: String on every request
  // objects — identical RPCs at every tier; want-list only
  RootTree(cs)                -> tree_id
  GetTree(id)                 -> Tree
  GetBlob(id)                 -> stream<bytes>
  // changesets
  GetChangeset(id)            -> Changeset
  PutBlob(stream<bytes>)      -> id        // for blobs > 1 MiB
  CreateChangeset(cs, inline_blobs) -> id   // blobs ≤ 1 MiB ride along
  // graph + queries
  MergeBase(a, b) -> opt<id>    IsAncestor(a, b) -> bool
  Diff(a, b)      -> stream<Change>
  Log(cs, limit)  -> stream<ChangesetSummary>
  Blame(cs, path) -> stream<BlameRange{ lo, hi, cs }>
  // refs
  ListRefs() -> …; GetRef(name) -> …
  CasRef(name, expected_cs, new_cs) -> { won | conflict(current) }
}
```

`Graft(cs, new_parent)` and `Harvest(cs)` are derived server operations:
Graft replays `cs`'s changes against `new_parent`'s tree (conflict → hard
error); Harvest asserts `IsAncestor(current_main, cs)` then CAS-moves
`main`.

## 6. bed's local state

```
.bed/config.toml    server address, repo, plot set
.bed/treestate      sqlite: path → (blob_id, mode, size, mtime_ns, hint)
.bed/objects/       local CAS cache, same 2-level sharding as loam
.bed/heads          local stack tip(s)
```

`status` uses mtime/size as hints and hashes only suspects; a
`--full-scan` flag forces the correctness path. `clone` materializes
nothing; `plot add` fetches exactly the requested subtrees.

## 7. Derived data (compost) in v0.1

- **Ancestry skip list** (segmented changelog over mainline), computed
  eagerly as changesets land; backing for MergeBase/IsAncestor and blame
  skips.
- **Blame walk**: first-parent chain; skip any segment whose bounded
  path-summary doesn't contain the path; follow renames via `src_path`.
- Everything derived is a **cache**: wipe + rebuild must converge to
  identical state (verified in M6).

## 8. Milestones and verification criteria

Each milestone lists deliverables, concrete verification, and the
**right-thing signal** — the property that would be absent if we had built
the wrong abstraction.

---

### M0 — Canonical model · wk 1–1.5

**Deliverables:** `docs/canonical-encoding.md` (§4 as code-auditable
tables); `gardenbed-model`: `Id`, `Changeset`, `Change`, blob/tree types;
encoder/decoder; fuzz targets for the decoder.

**Verification**
1. Golden vectors: ≥ 10 hand-built objects, exact hex committed as fixtures.
2. Roundtrip property: arbitrary generated changesets encode → decode →
   re-encode to identical bytes; `id` stable.
3. Mutation rejection: fuzz decoder 1 CPU-hour — truncation, bit flips, and
   overlong varints must never panic, only reject.
4. **Cross-language canonicality:** an independent Python decoder, written
   from the spec document alone, reads the fixtures and recomputes SHA-256
   Ids; all must equal Rust's. (Catches Rust-isms leaking into the format.)
5. Order-independence: constructing the same changeset with shuffled field
   population order yields identical bytes.

**Right-thing signal:** the format is a *spec*, not an implementation
detail — a second language can interoperate from the document alone.

---

### M1 — loam + seedbed (storage) · wk 1.5–3

**Deliverables:** `BlobStore` fs impl (2-level sharding, `{len, zstd}` frame,
tmp+rename atomic writes); `MetadataStore` sqlite impl (WAL; changesets,
refs with CAS column, git-SHA mapping); in-memory impls for tests.

**Verification**
1. Torn-write torture: loop { put blob, SIGKILL process } × 1000 — after
   each kill every stored object reads back byte-exact (SHA-256 verified) or
   absent; a truncated object must never be observable.
2. CAS race: 32 threads CAS the same ref — exactly one winner, 31 clean
   losses, final value == winner's.
3. Immutability: putting an existing Id with different bytes is an error
   (content addressing is load-bearing).
4. Crash-integrity: after the torture loop, `PRAGMA integrity_check` ok;
   WAL recovery replays with no lost committed changesets.
5. Throughput baseline recorded (puts+gets/sec at 1M objects) for CI trend.

**Right-thing signal:** storage is crash-safe *because* objects are
content-addressed and writes are atomic — not because of a journal we
bolted on.

---

### M2 — Tree derivation, diff, object API · wk 3–5

**Deliverables:** server-side `tree(cs)` derivation (apply changes to parent
tree; only touched dirs); tree cache in loam; tree-diff; object operations
as a Rust trait surface (gRPC wrapper arrives in M4). Harness crate, part 1:
seeded history generator + git materializer (renders our changesets into
real git commits via plumbing, giving us `git` as an oracle).

**Verification**
1. Tree equality: for random histories, recursive listing of `tree(cs)`
   equals `git ls-tree -r` — same path sets, same modes, same contents
   (compare via content; blob id spaces differ by design, D2).
2. Diff equality: our `Diff(a, b)` path/op classification equals
   `git diff-tree -r` (rename detection off on both sides in M2).
3. Content-addressing property: identical tree content produced via
   different histories → identical tree `Id`.
4. Derivation locality: deriving a tree for a 100-file change on a 1M-file
   repo writes ≤ 2 × (changed directories) new objects — derivation must
   touch only the dirs the change touches.

**Right-thing signal:** derivation locality (criterion 4) — commit cost
scales with change size, not repo size. This is the Scion property showing
up in our data structures for the first time.

---

### M3 — rootstock import + full differential harness · wk 5–7

**Deliverables:** import from a local git path and via fetch; topological
ingestion; octopus merges; git-SHA mapping table; incremental re-import;
force-push handling. Harness part 2: comparators (content, graph, log) and
corpora management (pinned snapshots).

**Verification**
1. Content fidelity: for random histories (linear + merges + octopus + renames),
   for **every** changeset and path: `file(path@cs)` == `git show
   <mapped_sha>:<path>`. Full sweep on a 10k-changeset synthetic corpus.
2. Graph fidelity: parent structure identical; mapping is a bijection
   (every git SHA ↔ changeset id, invertible).
3. Incrementality: import repo, add commits upstream, re-import — object
   write count == exactly the new commits' objects; importing an unchanged
   repo twice writes zero new objects.
4. Force-push: rewritten upstream re-imports cleanly — refs move, old
   objects remain (harmless), mapping has no duplicates or dangling rows.
5. Real corpora: pinned snapshots of ripgrep, cpython, rust-lang/rust
   import clean; 1,000 random (path, rev) pairs sampled from each and
   compared to `git show` — 100% match. Import throughput recorded
   (accepted cost of D8; no hard gate in v0.1).

**Right-thing signal:** the mapping is a bijection and import is
idempotent — git is a *peer* we translate losslessly, not a legacy format
we scrape.

---

### M4 — gRPC server + bed read path · wk 7–9

**Deliverables:** `.proto` + tonic services (§5); `bed clone / goto / plot /
file / log / diff / status`; `.bed/` treestate + local object cache.

**Verification**
1. Byte fidelity: after `bed clone` + `bed plot add`, every materialized
   file equals `git show` byte-for-byte; `bed status` reports clean.
2. Output parity: `bed log` and `bed diff` match git's on all corpora
   (documented format mapping; structural equality, not byte-equality of
   rendering).
3. Resumability: SIGKILL `bed` mid-clone at k% progress, restart — clone
   completes and the server's request counter proves **zero objects were
   fetched twice** (want-list + cache working as designed).
4. Perf budgets (localhost, recorded as bench baselines, CI-gated at +20%):
   sparse clone of a 1k-file plot < 5 s · warm `status` on 10k files
   < 500 ms · cold `bed file` p95 < 50 ms.
5. Offline behavior: `status` works with the server down; `file`, `goto`
   fail with clear errors, never half-states.

**Right-thing signal:** criterion 3 — resumability and cacheability fall
out of want-list negotiation for free; if we ever need "retry logic" for
object fetches, the protocol is wrong.

---

### M5 — Write path: sow, graft, harvest, export · wk 9–11

**Deliverables:** `bed sow` (two-phase upload; > 1 MiB blobs via PutBlob);
treestate update; stack heads; server-side validation; `Graft` (linear,
conflict = hard error); `harvest` (fast-forward CAS with ancestry
precondition); rootstock export via `git fast-import`.

**Verification**
1. **Size-independence (the Scion test):** identical 100-file change sown
   on synthetic repos of 10k and 1M files — p50 sow latency ratio ≤ 2×.
   Nightly bench, CI-gated.
2. Concurrent harvest: 16 threads harvest distinct changesets — exactly one
   wins per ref position; losers get a clean, actionable conflict message;
   no partial state visible at any point.
3. Graft correctness: rebasing random stacks onto a moved main produces
   trees equal to the independently computed expectation (replay-on-new-
   parent); any semantic conflict (same path, both sides modified) is a hard
   error with the conflicting paths listed.
4. **Export roundtrip:** repo X imported → exported → `git fsck` clean;
   original commits reproduce **identical git SHAs** (D6 + git-native
   timestamps make this exact); sown changesets appear as valid git commits
   whose trees match ours.
5. Crash mid-sow: SIGKILL between PutBlob and CreateChangeset → retry
   succeeds; orphaned blobs are unreferenced (harmless by construction); no
   reachable inconsistency.

**Right-thing signal:** criterion 1 — if sow latency cared about repo size,
the changeset design is wrong and everything downstream inherits the flaw.
This is the milestone where the architecture proves itself.

---

### M6 — Blame + ancestry skip list · wk 11–12

**Deliverables:** segmented changelog (eager on mainline); blame walk with
rename following; `bed blame`.

**Verification**
1. **Semantic anchor:** our blame ranges == `git blame --first-parent` on
   all corpora + 1,000 random histories, including rename-heavy ones
   (attribution mapped through the git-SHA table). Any mismatch is either
   fixed or documented as an explicit, reproducible divergence — silent
   disagreement is a release blocker.
2. Latency curve: blame vs history length {1k, 10k, 100k, 1M commits} grows
   ≤ O(log n) empirically (log-log slope < 0.3); gate: 100k-commit blame
   < 200 ms server-side.
3. Rebuild determinism: wipe all derived data → rebuild → byte-identical
   derived state, identical answers.

**Right-thing signal:** criterion 2's flat curve — the skip list exists so
blame cost doesn't track history length; if the curve is linear, the
derived-data framework isn't earning its keep.

---

### M7 — MCP surface · wk 12

**Deliverables:** `gardenbed-mcp` with tools `log`, `diff`, `blame`,
`file`; session docs; a scripted example agent.

**Verification**
1. Parity by construction: MCP tools call the same service layer as the
   CLI — asserted by shared-code tests, plus output-parity checks on all
   corpora.
2. **Zero-checkout contract:** the MCP harness runs in a container with no
   `.bed` directory anywhere and still answers correctly — agents must not
   need working copies.
3. Scripted QA: 20 canned questions over the corpora ("who last touched
   line N of X", "what changed between A and B") — 100% correct against
   harness truth.

**Right-thing signal:** criterion 2 — "the working copy is optional" is a
claim about architecture; this milestone is where it stops being a slogan.

---

### M8 — Hardening + v0.1 release · wk 12–13

**Deliverables:** release binaries; `demo/run-v0.1.sh`; chaos suite; fuzz
sweep; benchmark baselines in CI; docs (quickstart, protocol, encoding).

**Verification**
1. North-star demo (§0) green from a clean container — every assertion
   scripted.
2. Chaos: SIGKILL the server during each RPC class × 100 iterations —
   clients fail cleanly or succeed; after restart, full verification pass
   (loam checksum sweep + `integrity_check` + derived-data rebuild
   determinism) is green.
3. Fuzz: 24h cargo-fuzz across decoder, tree-apply, diff, import parser —
   zero crashes.
4. All perf budgets from M4/M5/M6 hold in CI against committed baselines;
   > 20% regression fails the build.

## 9. Verification infrastructure

- **`harness` crate** (new, M2–M3): seeded history generator; git
  materializer (subprocess `git` as oracle); comparators for content,
  graphs, diff, blame; corpus management with pinned SHAs.
- **Corpora:** synthetic (10k–100k changesets) for CI; real pinned snapshots
  (ripgrep, cpython, rust-lang/rust ≥ 1 GB) for nightly.
- **`bench` crate:** criterion suites with baselines committed; CI gates on
  +20% regression; nightly runs the full matrix including the 1M-file
  size-independence test.
- **Chaos + fuzz:** process-kill harness and cargo-fuzz targets listed per
  milestone; nightly long runs.
- **CI policy:** every milestone's verification becomes a CI job when the
  milestone lands and runs on every subsequent PR — regressions in *earlier*
  milestones fail later PRs.

## 10. Definition of done (v0.1)

1. The §0 demo passes, scripted, from a clean container.
2. **Zero silent divergences from git** on covered semantics: content@rev,
   tree listing, diff, first-parent blame, log structure. Divergences are
   allowed only if documented with a repro.
3. Every milestone's verification runs green in CI on current main.
4. A newcomer can go from `cargo install gardenbed` to sowing a change
   following only the quickstart.

## 11. Risks

| Risk | Mitigation |
|---|---|
| gitoxide gaps (rename detection, pack writing) force subprocess fallbacks | D6/D8 embrace this for v0.1; native replacements are their own milestones with the same differential criteria |
| sqlite contention under concurrent sows | WAL mode + busy timeout; the M5 concurrency test exists to catch it early |
| `git blame --first-parent` edge cases (empty files, CRLF, weird encodings) | corpus-driven: generator emits these deliberately; mismatches become fixed cases or documented divergences |
| Import throughput of D8 subprocess diffs | accepted, measured (M3.5); optimized in v0.2 without changing semantics |
| Scope creep (review UI, IAM, merge) | §1 out-list is contractual for v0.1; changes require editing this doc first |
