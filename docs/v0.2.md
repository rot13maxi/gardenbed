# gardenbed v0.2 — design and verification plan

Status (October 2026): M9–M19 are implemented and landed on
main (verification evidence in each milestone's outcome notes); M13
(garbage collection) landed after round-4 review (2026-10-19). The
document keeps the v0.1 method: decisions name what they reject, milestones
carry verification criteria, and every criterion implies a right-thing signal —
the property that would be absent if we had built the wrong abstraction. The
scope of record is the v0.1 out-table ([v0.1.md](v0.1.md) §1); this document makes
that scope concrete. Research grounding: file citations are load-bearing claims
verified against the current tree (October 2026, post-terminology-rename).

## 0. North star

v0.2 proves concurrent, multi-repository, occasionally-offline work end to end.
The acceptance test is an automated demo (`demo/run-v0.2.sh`) that must pass
from a clean container:

1. Import a real history into a named repository; a second repository is
   created and served by the same server process.
2. Two workers commit against `main` from the same repository. One publishes;
   the other runs `bed merge main`, resolves a listed conflict, re-merges, and
   publishes — the merge changeset lands on `main` with both parents.
3. The server stops. A third worker commits three changesets offline. The
   server restarts, `bed sync` replays them, `bed publish` fast-forwards.
4. `gardenbed-server gc --dry-run` reports exactly the orphans the run planted;
   `gc` deletes exactly those; a second run deletes nothing.
5. A change touching a > 1 MiB blob round-trips through commit, clone, and
   export with the blob id unchanged (chunked storage, same identity).
6. Export to Git: `git fsck --strict` clean; SHA roundtrip 100%; an imported
   signed commit exports with its original SHA and signature intact.
7. Two working copies served by the local daemon: the second copy's warm fetch
   issues zero new server-side object requests for shared content.
8. An MCP client answers `log`/`diff`/`file`/`blame` with no working copy
   anywhere on the machine.

The acceptance test is `demo/run-v0.2.sh`: it asserts all eight steps above
(one `✓` line per claim, exiting non-zero on the first failure) over a
deterministic synthetic git history; set `GARDENBED_DEMO_CORPUS` and the same
assertions run over a real corpus (the demo makes a scratch clone and appends
one commit carrying the paths the later steps exercise), plus the auth-token
seam: an anonymous clone is denied with the actionable message and a
`GARDENBED_TOKEN` clone/commit/publish succeeds. It imports one history
into two named repositories served by one process, lands a two-parent merge
after a real conflict resolution, drains three offline changesets through
`bed sync`, verifies gc collects exactly the planted orphans and nothing the
second time, round-trips a > 1 MiB GBLO2 blob, exports with `git fsck
--strict` clean and a 100% changeset↔git-SHA mapping (a hand-built `gpgsig`
commit exports verbatim), proves a warm daemon adds zero server-side
GetTree/GetBlob requests (with a cold-cache negative control), and answers
MCP `log`/`diff`/`file`/`blame` with no working copy and the server stopped.
The nightly CI release canary runs it on `main`.

A human should never have to eyeball this — the script asserts each step.

## 1. Scope

**In:** server-side merge (two parents, content resolution), multi-repository
server, garbage collection of unreferenced objects, blob chunking (storage
only), offline commit queue with explicit sync, local daemon (shared cache and
watching), native pack export, import fidelity for signed/non-UTF-8/extra-header
commits, render-level rename and gitlink parity.

Additional features originally deferred to v0.3 have already landed:
read-only FUSE checkout (`bed mount`) and optional token authentication with
per-repository roles (`serve --auth`). See [architecture.md](architecture.md)
and [cli.md](cli.md). Milestone implementation does not imply every original
verification gate is closed; see [current status](status.md), especially M18.5.

**Out (and when it returns):**

| Deferred | Lands | Why |
|---|---|---|
| Regional cache tier | v0.3 | the want-list protocol makes it landable at any time with no protocol change, and `bed`'s client-side cache leaves no demand signal today (§5) |
| Windows, LFS, submodule recursion | v0.3 | unchanged |
| History pruning (changeset + git-mapping rows) | later | breaks the mapped-frontier incremental-import proof and the git↔changeset bijection; design note in §7 |
| Chunk-level dedup across blob versions | v0.3 | the real chunking payoff, but it changes upload semantics; GBLO2 (§7) is deliberately the enabling format |
| Per-chunk streaming `GetBlob` | later | protocol change; the server already materializes blobs in memory |
| Combined (merge) diff rendering | later | renderer-only; `--diff-merges=first-parent` stays the documented parity target |
| Rename-aware merge; native octopus | later | rename-blind two-parent merge first (§4) |
| Retiring the `git diff-tree` rename subprocess (D8) | when gitoxide ships git-parity similarity scoring | measured in §8 |

## 2. Architecture (v0.2)

```text
bed ──gRPC (TCP)────────────── gardenbed-server (multi-repository)
                                 │   <root>/<repo>/objects + metadata.sqlite3
bed ──unix socket── gardenbed-daemon ──gRPC──┘            (optional)
                      ├─ shared object cache ($XDG_CACHE_HOME/gardenbed)
                      └─ per-working-copy filesystem watchers
gardenbed-mcp ──in-process Repo (same service layer, no RPC)──┘
```

- The server serves N repositories from one process. A repository is a
  directory; the wire's `repo` field — present on every request since day one —
  selects it. Object and metadata stores stay per-repository; nothing in the
  storage layer learns that other repositories exist.
- The daemon is an optional local tier: a caching gRPC proxy plus filesystem
  watchers, speaking the identical RPC surface. `bed` falls back to the
  embedded client whenever the daemon is absent; outputs and on-disk state are
  identical either way.
- Writes remain: `PutBlob` + `CreateChangeset` (two-phase), `Rebase`,
  `Publish`, and the new `Merge`. Publication is still a compare-and-swap;
  merges change ancestry, not the ref protocol.
- Export stops shelling out to git entirely: the Git bridge writes packs
  natively in both directions.
- The daemon is what finally serves the `unix://` scheme the client has
  accepted since v0.1; the server itself stays TCP-only.

## 3. v0.2 decisions

- **D9 — Merge is a server-side derived operation: one `Merge` RPC, two
  parents, zero new storage.** Rejected: client-side merge via
  `CreateChangeset` (breaks the zero-checkout contract; sparse working copies
  do not hold full trees) and deriving Merge from Rebase (replay has no
  base-side content to line-merge). Determinism makes races benign: concurrent
  identical merges re-put identical canonical bytes — one changeset id.
- **D10 — Merge changesets take `parents = [ours, theirs]` and a change list
  vs `ours`; tree derivation is untouched.** The merge computes a 3-way tree
  over (merge base, ours, theirs) and emits `Add`/`Modify`/`Delete` changes
  against ours, so the existing first-parent derivation rule reproduces the
  merged tree and every downstream consumer (validation, export, blame) sees an
  ordinary changeset. Content resolution reuses the xdiff port; the merge is
  rename-blind (§4).
- **D11 — Merge conflicts are a hard error listing every conflicting path;
  nothing is stored.** Rejected: conflict-marker merges — changesets are
  immutable truth; a marker merge could be published and bake failed state into
  history permanently. Resolution belongs in the working copy; a crash mid-merge
  leaves only unreferenced merged blobs, harmless by construction.
- **D12 — One directory per repository under the server root; the directory is
  the registry; legacy roots auto-serve as `default`.** No registry file (a
  registry can drift from the tree; a directory listing cannot lie). Migration
  is zero-action for existing roots; `gardenbed-server move` renames explicitly.
- **D13 — Repositories resolve through a lazy map with bounded open handles.**
  Per-repository metadata databases keep the write lock per-repository
  (cross-repo write parallelism for free); `--max-repos` caps open handles;
  unknown names fail `not_found` listing the served names. Rejected: one shared
  metadata database keyed by repo (would make the compare-and-swap write lock a
  server-global bottleneck).
- **D14 — GC = metadata-defined reachability, age-guarded sweep, offline by
  default.** The mark is a pure function of SQLite state; the sweep unlinks
  only objects unreachable at mark time and older than a grace period.
  Changeset rows and git-mapping rows are never collected in v0.2.
- **D15 — GBLO2: blobs above 1 MiB store content-defined chunked; identity,
  wire protocol, and the object-store trait are unchanged.** Chunking is a
  storage detail exactly as compression is (D2's rule, extended).
- **D16 — Tree derivation stays eager.** Lazy derivation already exists on the
  read path; validation certificates durably pin certified roots; skipping
  write-path tree objects would move the same work onto the clone/export
  latency budget for no measured win.
- **D17 — The offline commit queue stores canonical bytes and ids, nothing
  else.** A changeset's id is `SHA-256(canonical bytes)`, computable locally
  from the model crate; replay is the existing two-phase upload, idempotent
  end to end because ids are content addresses. Rejected: a second sqlite file
  (cannot share the recovery transaction), a server-side queue (needs a
  connection — defeats the purpose).
- **D18 — One daemon per machine: caching proxy plus watchers, never an owner
  of checkout or status logic.** All `.bed` writes stay in `bed`; the daemon
  never opens the working-copy index. Rejected: daemon-owned status logic
  (would fork behavior between daemon-present and daemon-absent modes).
- **D19 — Daemon-first endpoint resolution with transparent embedded fallback,
  no config change.** Discovery is environment + one fixed socket path;
  `.bed/config.toml` gains no key (its schema rejects unknown fields, so no
  key keeps v0.1 files loading byte-compatibly). Fetch RPCs retry once against
  the embedded client on daemon death; writes are never blindly retried.
- **D20 — A native pack writer replaces `git fast-import`; export computes git
  SHAs itself and asserts each against the git-mapping table.** Full objects,
  no deltas; SHA-1. Rejected: staying on fast-import — it has no grammar for
  extra commit headers, which is the root cause of the signed-commit and
  unmodeled-header divergences.
- **D21 — Imported history exports verbatim: commits whose bytes are not
  provably reconstructable are captured raw at import in a sparse side table.**
  The object *is* the original, so the SHA is original by definition — no
  re-signing, no canonical-format change, no version bump. The String-typed
  model stays the display truth; raw bytes are identity/export truth only.
- **D22 — Rename rendering comes from recorded facts, not a similarity
  heuristic.** Changeset-scoped diffs reuse the recorded `Op::Rename`;
  two-sided diffs pair identical-blob delete+add entries at render time — the
  deterministic rule `commit` already applies. Moved-and-edited files keep
  delete+add rendering.
- **D23 — Gitlink pointer hunks render from the real submodule SHA already
  stored** (the canonical gitlink blob id is the upstream 20-byte SHA-1
  zero-padded to 32). Render-local; no format change; retires the
  binary-differ divergence for pointer changes.
- **D8 stays.** gitoxide's rename tracking exists but scores similarity
  differently from git (different thresholds, per-destination ranking instead
  of git's global candidate matrix); retiring the `git diff-tree -M`
  subprocess now would trade a measured, accepted cost for a new
  rename-classification divergence. Retirement trigger: upstream git-parity
  similarity scoring; then port under the same differential criteria. Optional
  v0.2 throughput work: parallelize diff-tree batches across subprocesses —
  semantics untouched.

## 4. Merge semantics (D9–D11)

**Representation.** A merge changeset has `parents = [ours, theirs]` (first
parent remains delta base and blame mainline — the git convention). Its
changes are the diff `tree(ours) → merged_tree`, so `apply(changes,
tree(parents[0]))` reproduces the merged tree through the unchanged derivation
rule and validation certificates apply without modification (the store already
requires every parent certified, including beyond the first).

**The 3-way tree merge.** A recursive walk over `(base, ours, theirs)` trees:

1. Trivial rules first: two sides equal → that value; one side unchanged from
   base → the other side. Content-addressed equality prunes untouched subtrees
   before any blob read; only touched directories are re-encoded.
2. Regular/executable leaves differing on both sides get a per-file 3-way
   merge of (base, ours, theirs) blobs on the existing xdiff port: change
   regions from both sides, overlap-tested in base coordinates like git's
   `xdl_merge`; non-overlapping regions auto-combine, overlapping regions
   conflict.
3. Mode merge follows the same trivial rules; symlinks and gitlinks are atomic
   (id equality only).
4. Directory-level conflicts reuse the tree applier's rules: file↔directory on
   both changed sides, delete-vs-modify, add/add, writes under concurrently
   replaced subtrees.

**Conflicts.** Any conflict fails with `FAILED_PRECONDITION`
(`merge conflicts on: …`), listing every conflicting path collected before
returning — the rebase contract. Nothing partial is ever stored.

**RPC and CLI.** `Merge` joins the write-ops group:
`Merge{repo, cs, target, message, author, committer} → {id, up_to_date}`.
`bed merge <target>` merges the target into the current changeset (the
session model every write command already uses). When `target` is already an
ancestor, the response is `up_to_date` with the current id — no changeset.
Unrelated histories (no merge base) fail naming the operation. The message
defaults to a synthesized `merge <target>` when `-m` is absent.

**Display.** `bed log` renders date-ordered across all lineages (parents ride
the wire today). `bed blame` is unchanged: first-parent lineage (D7) already
handles merge changesets, which import has always produced. `bed diff` of a
merge is against the first parent — parity target
`git diff-tree --diff-merges=first-parent`. The MCP surface is unchanged.

**Cost.** O(union of paths changed on either side); content-addressed trivial
rules prune untouched subtrees. Two-parent only in v0.2 — n-parent changesets
still arrive via import and export; octopus is sequential merges later.

## 5. Multi-repository server (D12–D13)

**Layout.** `<root>/<repo>/objects` + `<root>/<repo>/metadata.sqlite3`. A
repository exists iff its directory holds `metadata.sqlite3` or `objects/`.
Names: 1..=64 bytes of `[A-Za-z0-9._-]`, not starting with `.`, case-sensitive;
reserved: `objects`, `metadata.sqlite3`, `seedbed.sqlite3`, `git-mirror.git`,
`tmp`.

**Migration.** `serve` detects a v0.1 root (`metadata.sqlite3` or `objects/`
at the top level) and registers it as repository `default` — the name both
`bed clone` and `gardenbed-mcp` already fall back to — so every existing root
keeps serving unchanged. `gardenbed-server move --root DIR --into NAME`
performs the two renames; both stores are path-free and self-contained, so
history is byte-identical after the move (verified, M11.4). `import`/`export`
gain `--repo NAME`; per-repository mirrors live at
`<root>/<repo>/git-mirror.git`.

**Serving.** A `RepoSet` (`RwLock<HashMap<name, Arc<RepoHandle>>>`) opens
`<root>/<repo>` on first request, singleflighted through the map lock; open
cost is two directory creations plus one sqlite open. `--max-repos` (default
256) caps open handles LRU-style, evicting only handles with no in-flight
users; eviction closes the sqlite connection and releases the ≈64 MiB engine
caches. Every handler's `repo` field resolves through this one function —
the repository-resolution seam; optional token authorization now runs in
`GardenbedService::authorize` before store access. Unknown names fail
`not_found("repository <name> not found (this server serves: …)")`; invalid
names fail `invalid_argument`; empty stays `invalid_argument`.

**Addresses.** `bed clone http://host:port/<repo>` parses the path client-side
(`--repo` wins on conflict; no path ⇒ `default`); `gardenbed-mcp --repo`
becomes load-bearing. `GetStats(repo)` returns that repository's counters.

**Cache-tier verdict.** A regional cache tier would be a read-only tier
speaking the read RPCs in front of an origin, backed by its own object store.
The protocol already guarantees feasibility — every request names a
content-addressed object and every tier hash-verifies on read, so a corrupt
tier can never poison anyone. Deferred: multi-repository lands first to scope
and route by name; the client cache absorbs re-reads today; and deferring
costs nothing architecturally.

## 6. Client: offline queue and daemon (D17–D19)

**Offline commit.** When the server is unreachable (`Unavailable` connect
failures only — never auth or refusal errors), `bed commit` completes
everything up to the upload: scan → changes → validate → `cs.id()` computed
locally → stage all changed blob contents into `.bed/objects` → one sqlite
transaction inserting the pending rows → the exact online-commit state move
(treestate refresh, heads tip, current changeset). Tables in `index.sqlite3`
(`CREATE TABLE IF NOT EXISTS`, so v0.1 files load unchanged):

```sql
pending(seq INTEGER PRIMARY KEY AUTOINCREMENT,
        cs_id BLOB UNIQUE NOT NULL, parent BLOB,
        canonical BLOB NOT NULL, message TEXT, created INTEGER)
pending_files(seq, path, blob_id, mode, size, mtime_ns)
```

`pending_files` holds the treestate patch needed to re-apply the state move
idempotently: recovery completes the move when the newest row's `parent`
equals the recorded current changeset (heads appends become check-then-append
in the recovery path only). Chained offline commits parent onto the previous
pending tip. `bed sync` drains oldest-first — heavy blobs via `PutBlob`, then
`CreateChangeset` within the same inline budgets — deleting each row only
after its acknowledgment. Replay is idempotent without protocol change: the
server's existing-id path is an idempotent re-put, `PutBlob` likewise, and
orphaned blobs from a killed sync are unreferenced and harmless (M5.5's
property extended from one commit to a queue).

**Refusals.** `switch`, `rebase`, and `publish` refuse while the queue is
non-empty (online or offline), naming `bed sync` and the pending count.
`status` prints `N pending commit(s) not yet on the server — run bed sync`.
`bed log`/`diff` with a pending tip fail with a queue-aware error; client-side
history stitching over pending canonical bytes is deferred.

**Daemon.** `gardenbed-daemon serve` (the placeholder crate exists) listens on
`$XDG_RUNTIME_DIR/gardenbed/daemon.sock` (0700; `GARDENBED_DAEMON` overrides
or disables). It implements the generated `Gardenbed` trait, forwarding every
RPC verbatim — the `repo` field rides untouched — and answers `GetTree`/
`GetBlob` cache-first from a shared object store at `$XDG_CACHE_HOME/gardenbed`
(one store, same envelope and sharding, write-through after each upstream
fetch). A small sidecar service adds `Ping` and
`Register(state_dir) → generation counter`: a recursive filesystem watch on
the working-copy root (new `notify` dependency), excluding `.bed` and checkout
staging entries. `bed status` returns the last cached report when the
generation is unchanged; any event or watcher absence falls back to today's
scan exactly — the mtime/size hint machinery stays the correctness fallback.
Peer-uid is checked before serving write RPCs. Endpoint resolution probes the
daemon first, then `config.server`; fetch-phase RPCs retry once against the
embedded client on daemon death.

## 7. Object-store lifecycle (D14–D16)

**Roots and mark.** Reachable = every ref tip, closed recursively over all
parents of stored changeset canonical bytes; every blob id referenced by a
non-gitlink change of a stored changeset; every validation-certificate root
tree id and every `derived(kind='tree')` id, closed transitively over tree
payloads. Changeset rows and git-mapping rows are never collected in v0.2 —
the bijection, mapped-frontier incremental import, and export topology assume
complete rows (history pruning stays out of scope). Derived non-tree caches
are rebuildable and never roots. The mark materializes into SQLite temp tables
(`gc_live`, `gc_seen` with size + mtime captured during the walk), so RSS stays
bounded at ten-million-object scale and the report is one SQL join.

**Sweep.** One walk over the 256 shard dirs; unlink candidates = seen ∧ ¬live
∧ mtime older than `--min-age` (default 24 h). Plain `unlink` — no tombstones,
no staging renames: candidates are already unreachable, and POSIX unlink never
disturbs an in-flight read. The same walk reaps `.tmp-*` files older than
min-age — this is the real reaper `architecture.md` §9 currently claims but
never implemented; that section is corrected in the same change. The grace
period also covers a slow client's uploaded-but-unreferenced blobs, including
the interrupted-sync orphans the offline queue can leave.

**Operation.** `gardenbed-server gc --root DIR [--dry-run] [--min-age]
[--verify] [--force]`. `serve` holds a shared `flock` on `<root>/repo.lock`;
`gc` takes it exclusive, so the default stance is offline-first. `--force`
runs live with delta-marking (re-scans refs/certificates/changesets above a
rowid watermark) and aborts the sweep if an ingest lands mid-sweep. A crash
before the mark commits writes nothing; each unlink is independent, so
SIGKILL at any point leaves a sound store. The report counts scanned, live,
tmp reaped, deleted (blobs/trees), and bytes reclaimed.

**GBLO2 envelope.** Blobs with `raw_len > 1 MiB` store as one file:
`"GBLO2" | raw_len: u64 LE | chunk_count: u32 LE | chunk_count ×
{chunk_raw_len: u32 LE, chunk_comp_len: u32 LE} | chunk_count zstd frames`.
Boundaries come from FastCDC (min 64 KiB / avg 256 KiB / max 1 MiB) —
content-defined, hence deterministic for identical content. GBLO1 keeps
everything ≤ threshold byte-identically. Reads decode each chunk bounded by
its declared length and verify the reassembled content's SHA-256 against the
addressed id — the same torn/tamper guarantee as GBLO1; per-chunk checksums
buy nothing the whole-blob gate doesn't. `GetBlob`/`PutBlob` framing is
untouched; clients hash-verify and cache the reassembled GBLO1 form, so
chunking never crosses the `ObjectStore` trait. The chunk table at the 4 GiB
cap is ≤ ~786 KiB.

**Derivation verdict.** Stay eager (D16). The read path already derives on
demand when caches are cold, and certificates pin certified roots; the only
candidate was skipping write-path tree objects, which moves the same
O(change) work onto clone/export latency for no measured win against the
actual import bottleneck (the diff-tree subprocesses). Revisit on a profile
showing tree-apply dominating import.

## 8. Git bridge (D20–D23; D8 retained)

**Native pack writer.** Export writes a SHA-1 pack of full objects (no
deltas) plus a v2 `.idx` and loose-ref/HEAD updates. Object names are
computed, not observed: blobs `SHA1("blob <len>\0" + content)`; trees rendered
from canonical trees re-sorted into git's tree order (directories compare as
if suffixed `/`); commits from the existing reconstruction (identity bytes
verbatim, raw `±hhmm` offsets, root-from-empty, renames as `M`+`D`, gitlink
padding stripped). Every computed commit SHA is asserted against the store's
git-mapping row — drift is a hard error, never silent. gix-pack's encode path
is preferred (delta compression and bundled index writing are still unchecked
upstream; the index comes from the two-step create-index path); a ≤~300-line
hand-rolled writer is the pre-scoped fallback, decided by a spike gate at
milestone start. **Gate outcome (M17, decided): hand-rolled.** gix-pack 0.76's
index encoder (`index::encode::write_to`) is `pub(crate)`, and
`Bundle::write_to_directory` re-parses and re-verifies the whole stream to
build the idx — pure overhead when the writer already holds every offset,
CRC, and SHA (full objects, no deltas). Implemented as
`crates/git/src/pack.rs` (~500 lines including the read-back oracle).
Marks and the marks file retire from `ExportReport`.

**Import fidelity.** At import, in the same ingest transaction, commits whose
bytes are not provably reconstructable from the model — signature present, any
unmodeled header, any lossy byte, or header order ≠ reconstruction order —
are captured raw in `git_raw_commit(git_sha PRIMARY KEY, data BLOB zstd)`,
keyed like the git mapping (sparse by construction: ≈0 rows on the kernel
corpus). Export writes those commits verbatim; the re-import of an exported
signed history keeps the original SHA, so the git↔changeset bijection holds
instead of forking ids. Optionally the same mechanism stores raw *tree* bytes
for trees whose git rendering diverges (non-UTF-8 names, `100664` history) —
gated on the kernel import staying within ±20% of the recorded 278 commits/s;
if the gate fails, commit-bytes-only ships and the path-name half of the
non-UTF-8 divergence stays documented. v0.1 stores retire the affected
divergences by re-importing; changeset ids are stable because canonical bytes
are unchanged.

**Render rename pairing.** The renderer gains git's rename form —
`similarity index 100%` + `rename from`/`rename to`, extended-header order
pinned byte-for-byte against `git diff-tree -M -p`. Changeset-scoped diffs
(`bed diff <cs>`, and bare `bed diff`, which already resolves the first
parent) build entries from the recorded changeset — reusing its `Rename` ops
directly instead of re-deriving from trees; two-sided diffs pair identical-
blob delete+add entries at render time. Moved-and-edited files keep delete+add
rendering (no similarity heuristic; residual counted and documented). MCP
`diff` deliberately keeps its `--no-renames` letter parity. Every renderer
change lands with `git apply` tests — the QA-pass rule.

**Gitlink pointers.** The renderer strips the zero-padding (mirroring export's
stripper, refusing non-zero-padded ids loudly) and emits git's honest form:
`Subproject commit <sha>` add/delete hunks and the `@@ -1 +1 @@`
pointer-change hunk, replacing the binary-differ line. Render-local; the
stored sha *is* the pointer git would apply.

### M9 — merge core ✅ (implemented, `crates/derive/src/merge.rs`)

**Deliverables:** per-file 3-way content merge (`merge3(base, ours, theirs) →
merged bytes | conflict`) over the xdiff port; the 3-way tree walk emitting a
change list vs ours; `Engine::merge_changesets(ours, theirs)`; fuzz target
`fuzz_merge3`; harness additions — a genuinely divergent-pair generator (the
current generator's merges are deliberately redundant) and a
`git merge-tree --write-tree` oracle wrapper.

**Verification**
1. Differential oracle: for ≥ 1,000 generated merge triples (divergent
   histories, rename-free), per-path clean/conflict classification and every
   clean path's merged content equal `git merge-tree --write-tree`.
2. Hand-built classification matrix pinned as fixtures: trivial rules,
   non-overlapping hunks auto-merge, overlap → conflict, mode merge table,
   delete-vs-modify, add/add, file↔dir both-changed.
3. Derivation invariant: every successful merge satisfies
   `apply(changes, tree(parents[0])) == merged tree` — property-tested on all
   generated histories.
4. Determinism: the same triple yields identical merged bytes and changeset id
   across runs, engines, and wiped derived caches.

   `fuzz_merge3` 1 CPU-hour, zero panics.

**Right-thing signal:** merge introduces no new storage, no new truth, no new
validation path — its changesets derive through the unchanged first-parent
rule. If the engine needed its own object type, the changeset model is wrong.

**Deliverables:** `gc` subcommand (mark/sweep/report); batched metadata reads

### M14 — blob chunking (GBLO2) ✅ (implemented: `crates/store/src/fastcdc.rs`, GBLO2 envelope in `fs.rs`)

## 10. Verification infrastructure

The criteria below are the intended verification bar. For the actual CI
selection, opt-in suites, and still-open measurements, see
[verification coverage](status.md#verification-coverage).

- **Harness:** divergent-pair history generator (the current generator's
  merges are deliberately redundant); `git merge-tree --write-tree` oracle
  wrapper following the existing subprocess-oracle pattern; pack read-back
  oracle (decode writer output, byte-compare); GBLO2 torture fixtures.
- **Fuzz:** new targets `fuzz_merge3` and the pack writer; existing targets
  keep their corpora; decoder and tree-apply targets unchanged.
- **Chaos:** extensions for merge (M10.5), GC (M13.3), and every queue phase
  (M15.6), reusing the SIGKILL/restart/verify methodology.
- **Budgets and CI policy:** same as v0.1 — each milestone's verification
  becomes a CI job when it lands and runs on every later PR; budgets recorded
  with a +20% regression gate. New baselines: export wall clock, chunked
  put/get, GC dry-run time and RSS on the kernel store, warm status under the
  daemon.

## 12. Risks

| Risk | Mitigation |
|---|---|
| Merge classification diverges from git (hunk overlap, adjacency, modes) | differential oracle vs `git merge-tree --write-tree`; mismatches fixed or documented with a repro |
| Criss-cross histories have several maximal merge bases; our deterministic tie-break can differ from git's | documented divergence; the oracle compares single-base histories; recursive multi-base merge is a later decision |
| Rename-blind merge surfaces rename/rename as add/add and rename/delete as delete/modify | documented divergence; `src_path` keeps blame correct; rename-aware merge revisited with a dedicated rename model |
| GC collects a blob a slow client uploaded but has not referenced | min-age grace (24 h default) + the retry path re-uploads; `--force` delta-marks and aborts on mid-sweep ingest |
| Mark set exceeds memory at kernel scale | SQLite temp tables; RSS-gated budget criterion |
| A GC bug deletes a reachable tree | recoverable (certified/derived tree loss is a recompute miss); blobs get the conservative path |
| Pack writer emits bytes git rejects | read-back oracle in CI; `git fsck --strict` + `push --dry-run` in the demo; golden fixtures; fuzz target |
| gix-pack encode API gaps | spike gate at M17 start; hand-rolled ≤~300-line writer pre-scoped as fallback |
| Raw-capture growth on huge imports | sparse capture rule; zstd-compressed rows; kernel throughput gate (±20% of 278/s) |
| Verbatim export masks model drift | raw commits parsed-and-checked against recorded tree/parents before use; SHA asserted per export |
| git-apply regressions from new rename/subproject blocks | every renderer change lands with apply tests (QA-pass rule) |
| inotify storms from build tools | debounce + generation counter; any doubt falls back to today's scan — the watch can only make status slower, never wrong |
| Daemon socket trust | 0700 runtime dir; peer-uid check before write RPCs |
| Queue rows never drained | bounded by use; status warns past a threshold; replay streams per-row, memory O(1) |
| zstd version drift changes chunk frame bytes | identity hashes raw reassembled bytes; determinism pins boundaries |
| Auto-queue hides a typo'd server | the first output line names the queue; status counts pending; sync errors name the server until reachable |

## 13. Judgment calls made here (veto-friendly)

- `bed sync` as the drain command (alternative considered: `bed push`).
- Auto-queue on `Unavailable` connect failures only, never on refusals.
- Merge message synthesized when `-m` is absent.
- Up-to-date merges answer `up_to_date` rather than erroring.
- Two-parent `Merge` in v0.2; octopus later.
- Regional cache tier deferred to v0.3 (recorded in §1 and §5).
- GC offline-first with an explicit `--force`; `--min-age` default 24 h.
- GBLO2 threshold at 1 MiB (aligned with the inline limit, so existing heavy
  fixtures exercise the chunked path).
- Raw-tree capture gated on the kernel import throughput, not unconditional.
- `ExportReport` loses `marks_path` in v0.2 (breaking pre-release precedent
  already set by the terminology change).
- History pruning deferred with a design note (bijection + incremental-import
  contracts).
